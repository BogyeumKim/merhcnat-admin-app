# 기기 바인딩 / 추가 인증 설계 (클라이언트 관점)

서버 계약, DDL(MySQL), 규약은 `docs/backend-contract/`. 백엔드는 아직 없고 코드는 계약 확정 후 작성한다.

## 확정된 요구사항 (사용자)

- 유저 테이블의 OTP 타입: **`0` = TOTP(Google OTP), `1` = 그 외(문자/메일/카카오톡)**. 값은 관리자가 계정을 만들 때 발급되어 이미 저장돼 있다. 앱에는 회원가입이 없다.
- **TOTP(0):** 로그인할 때마다 OTP를 입력하고 서버가 바로 검증한다. 코드를 DB에 저장하지 않는다.
- **그 외(1):** **최초 1회만** 인증(기기 등록)한다. 이후 같은 기기의 로그인은 OTP 없이 ID/비밀번호만. 로그인 화면에서 **문자/메일/카카오톡 중 인증 수단을 사용자가 선택**한다. 서버가 랜덤 코드를 만들어 DB(새 테이블)에 저장하고 유저 테이블에 등록된 메일/전화/카카오로 발송, 사용자가 입력하면 서버가 DB로 검증한다.
- 기기가 바뀌면 "다른 기기에서 로그인했다"는 안내와 함께 인증하고, 통과하면 서버가 기기 정보를 교체한다.
- 한 기기에는 **한 userId만** (1:1). 다른 ID로 로그인하면 인증 후 기존 바인딩을 덮어쓴다 (아래 참고).
- 기기 정보(기기 값, push token 등)는 새 테이블에 저장한다. PK는 `userId`. DB는 MySQL.
- 기기 키쌍과 루팅 탐지는 이번에 구현하지 않는다.

## 재설치를 같은 기기로 알아보려면 (이전 권장안 변경)

이전에는 "재설치 = 새 기기"를 권장했다. 그건 모든 로그인에 OTP가 있다는 잘못된 전제였다. **그 외(1) 사용자는 최초 1회만 인증하므로 재설치를 새 기기로 취급하면 매번 재인증이 필요해 비용이 크다.** 그래서 재설치 후에도 알아보는 쪽으로 바꾼다.

| 플랫폼 | 수단 | 재설치 후 | 근거 |
| --- | --- | --- | --- |
| Android | `getAndroidId()` (`expo-application`) | **유지된다.** 앱 서명 키·사용자·기기 조합별 값. 공장 초기화/서명 키 변경 시 바뀜 | Expo Application 문서 |
| iOS | Keychain에 저장한 UUID (`expo-secure-store`) | **대개 남는다. 그러나 보장되지 않는다.** Apple DTS가 "구현 세부사항이며 문서화된 기능이 아니다"라고 했고, Expo 문서도 의존하지 말라고 한다 | Expo SecureStore 문서, Apple 개발자 포럼, Expo GitHub 이슈 |
| iOS | IDFV (`getIosIdForVendorAsync`) | **이 앱이 해당 벤더의 유일한 앱이면 재설치 때 바뀐다** (벤더의 앱이 모두 삭제되면 변경) | Expo Application 문서 |

결론: **Android는 안정적으로 가능하고, iOS는 "대개 가능하지만 보장 불가"다.** iOS는 IDFV로는 안 되고 Keychain UUID가 현실적인 유일한 수단이다.

**서버가 기준이고, 못 알아본 경우의 안전한 폴백이 있다**: 식별자가 사라져 못 알아보면 "기기 변경"과 같은 경로(안내 + 인증)로 처리한다. 즉 보존은 편의이고 틀려도 안전하다.

**클라이언트가 보내는 신호**
- `deviceId`: 앱이 처음 만든 랜덤 UUID(v4). `expo-secure-store`에 저장, iOS는 `keychainAccessible: WHEN_UNLOCKED_THIS_DEVICE_ONLY`(백업 복원으로 다른 기기에 따라가지 않음).
- `androidId`: Android만, `getAndroidId()` 값. **서버가 해시(HMAC)로만 저장**한다 (원본 저장 금지).
- 서버 판정: `deviceId` 일치 **또는** Android에서 `androidId` 해시 일치 → 같은 기기.
- 위조 위험: 보안 벤더 글은 식별자 바인딩이 위조에 약하다고 한다. 다만 `ANDROID_ID`는 앱 서명 키별로 범위가 정해진 값이라 다른 앱이 같은 값을 읽을 수 없고, 공격자가 피해자 기기의 값을 알아야 한다. 루팅된 피해자 기기에서의 추출은 막지 못한다 (이번에 구현하지 않는 항목).
- 개발 중 주의: 디버그/릴리스 빌드는 서명 키가 달라 `ANDROID_ID`가 다르다. 빌드를 바꾸면 새 기기로 보일 수 있다.
- **스토어 정책:** `ANDROID_ID` 등 기기 식별자는 Google Play/Apple의 개인정보·사용자 데이터 정책과 앱 개인정보 고지 요건이 있을 수 있다. 이 세션에서는 확인하지 못했다. 출시 전에 확인한다.
- 식별자 값은 로그/커밋/문서/예시에 남기지 않는다.

## 한 기기 = 한 userId (1:1) 정책

조사 결과(보안 벤더/은행 공지): 일부 은행은 계정당 한 기기만 허용하고(필리핀 RCBC Pulz는 2026-01부터 단일 기기), 새 기기는 기존 기기에서 승인하게 한다. **한 기기에서 여러 사용자가 로그인하는 경우를 다룬 자료는 찾지 못했다.** 일반적으로 바인딩은 기기와 계정에 묶이므로 다른 사용자가 오면 다시 바인딩해야 한다.

설계:
- DB: `user_device`의 PK는 `user_id`, `device_id`에 UNIQUE → 1:1.
- 사용자 B가 인증을 통과하고 기기를 등록하면, 그 기기가 사용자 A에게 묶여 있었을 경우 **A의 바인딩은 삭제**된다. A는 다음 로그인에서 새 기기로 취급되어 인증을 다시 한다. 이력(`user_device_history`)에 남긴다.
- 앱: 세션은 메모리에 하나뿐이므로 B가 로그인하면 A의 토큰은 사라진다 (앱은 영속 저장하지 않음). 서버에서 이미 발급된 A의 토큰은 만료(약 10분)까지 유효하며, 즉시 폐기가 필요하면 서버가 별도 처리한다.
- UX: 기기가 다른 사용자에게 묶여 있으면 "이 기기에서 다른 계정으로 로그인했습니다. 기기를 변경합니다" 안내. 여러 계정을 번갈아 쓰는 사용자는 전환할 때마다 인증이 필요하다 (비용 인지 필요).

## 로그인 흐름

```
앱                                           서버
 │ POST /v1/auth/login                         │
 │ { userId, password, device }  ─────────────▶│ 1. 비밀번호/허용 타입/점검 확인
 │                                             │ 2. 기기 상태: NONE | MATCH | CHANGED
 │                                             │
 │ [OTP 타입 1 + MATCH]  ◀── 200 { status: AUTHENTICATED, ... } + 토큰(응답 헤더)   ← OTP 없이 끝
 │                                             │
 │ [그 외] ◀── 200 { status: CHALLENGE_REQUIRED, challengeId, deviceState, methods }
 │   TOTP:  methods = [TOTP]  (MATCH여도 항상)
 │   타입 1: methods = [SMS, EMAIL, KAKAO]  (사용 가능한 수단만, 목적지는 마스킹)
 │
 │ [CHANGED/NONE] 안내 + 확인 ("기기를 변경하시겠습니까?")
 │ [타입 1] 사용자가 수단 선택 → POST /v1/auth/challenges/{id}/send { method }
 │                                             │ 서버가 랜덤 코드 생성 → 해시 저장 → 유저 테이블의 목적지로 발송
 │ 코드 입력                                     │
 │ POST /v1/auth/challenges/{id}/verify        │ 3. TOTP: 비밀키로 계산 / 그 외: DB 조회
 │ { code, confirmDevice } ───────────────────▶│ 4. 통과 시 기기 등록·교체 + 이력, JWT 발급
 │ 200 + 토큰(응답 헤더) ◀──────────────────────│
```

- `login`은 **두 가지 결과를 같은 200으로 구분**한다 (`status`로). OTP 타입 1 + MATCH면 바로 인증 완료, 그 외에는 챌린지다. 둘 다 오류가 아니라서 200이고, 오류는 problem+json(`api-conventions.md`).
- 챌린지는 사용자·기기에 묶인다. 다른 시도에서 받은 코드는 통과하지 않는다.
- **발송 목적지는 서버가 유저 테이블에서 꺼낸다.** 앱은 수단(`SMS|EMAIL|KAKAO`)만 고르고 번호/주소를 보내지 않는다. 화면에 보이는 목적지는 서버가 마스킹해서 준다.
- 앱은 "인증됨"을 판단하지 않는다. 서버만 판단한다. 인증 단계에서 요청을 자동 재시도하지 않는다.
- 입력 화면: 숫자 키패드, SMS 자동 입력(`textContentType="oneTimeCode"`, Android `autoComplete="sms-otp"`), 재전송 버튼(쿨다운), 입력값 로그 금지.

## 앱 구현 위치 (예정)

`features/auth/`: `api/`(login, send, verify), `mutations/`, `screens/`(로그인, 인증 수단 선택, 코드 입력, 기기 변경 확인), `model/`(`device-id`, `UserType`, 세션).

## 푸시 (Expo Push Service 권장, 구현은 사용처가 생길 때)

**권장: Expo Push Service.** 조사 결과 (벤더 블로그 여러 곳이 같은 내용, 수치는 Expo 공식 문서로 확인):
- Expo 앱에서는 Expo Push Service가 기본 선택으로 소개된다. FCM/APNs를 감싸서 Android/iOS를 같은 토큰 형식·같은 API로 다룬다. 직접 FCM/APNs는 Expo가 노출하지 않는 플랫폼 기능이 필요하거나 이미 FCM 파이프라인이 있을 때 선택한다.
- 서버(Spring Boot)는 `https://exp.host/--/api/v2/push/send` HTTP API를 호출하면 된다. 언어 제약은 없고, Expo가 직접 관리하는 SDK는 Node.js뿐이다 (Java 등 커뮤니티 SDK 있음).
- 공식 문서 기준: 요청당 최대 100개, 프로젝트당 초당 600건, 티켓은 "Expo 서버가 받았다"일 뿐 사용자가 받았다는 뜻이 아니며 영수증은 약 15분 후 조회/24시간 후 삭제, `DeviceNotRegistered`는 해당 토큰 발송을 중단, 페이로드 4096바이트 초과는 `MessageTooBig`. **액세스 토큰**(EAS 대시보드에서 활성화)을 켜면 무단 발송을 막을 수 있다.
- 요구사항: `projectId`(EAS 프로젝트)와 FCM(Android)/APNs(iOS) 자격 증명을 EAS에 등록. **EAS development build를 쓰지 않아도** 푸시를 위해 EAS 프로젝트와 자격 증명은 필요하다. 개발 빌드(Expo Go 아님)가 필요하고 로컬 prebuild 빌드가 이에 해당한다.
- 단점: Expo 토큰은 FCM/APNs 토큰이 아니라서 나중에 Expo를 떠나면 토큰을 다시 받아야 한다. 메시지가 Expo 서버를 거친다 (Expo가 내용을 어떻게 다루는지는 이번에 확인하지 못했다). 금융 앱이므로 **푸시 본문에 민감 정보(금액, 가맹점명, 개인정보)를 넣지 않고** 일반 문구만 보내 앱이 열린 뒤 조회한다 (자료의 "OS가 보여줄 것만 보내라"는 조언과도 맞는다).
- 푸시 토큰은 실행 중에도 바뀔 수 있다(`addPushTokenListener`). 로그인과 변경 시 서버에 갱신하고, Android 13+는 토큰을 받기 전에 알림 채널을 먼저 만든다.
- 푸시 토큰은 식별자이므로 로그/커밋/문서에 남기지 않는다.
- **지금 앱에는 푸시를 쓰는 기능이 정해져 있지 않다.** 무엇을 알릴지(거래 알림 등)가 정해질 때 구현한다. `user_device.push_token`은 비워 둬도 된다.
